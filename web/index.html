      About the compiler
      

        
What it does

        

          Compiles ASN.1 to Rust bindings for the
          rasn
          framework, or to TypeScript types. The parser is rasn-compiler,
          compiled to WebAssembly.
        

        
Why it runs in your browser

        

          GSMA specifications are not redistributable and schemas derived from them
          inherit that, so there is no server to send them to. The page is static:
          no backend, no logging, no rate limit, no auth.
        

        
Formatting

        

          Upstream, the Rust backend pipes its output through rustfmt, and
          the TypeScript backend has no formatter at all. A browser cannot spawn
          processes, so both arrive unformatted here and are laid out locally. The
          results are checked rather than assumed: the Rust output passes
          rustfmt and cargo check against rasn 0.28,
          and the TypeScript output passes tsc --noEmit.
        

        
What it does not do

        
    
          
  • It does not decode mccMnc. SGP.22 declares it
            OCTET STRING (SIZE(3)) "coded as 3GPP TS 24.008". The ASN.1 says
            nothing about the internal layout, so a schema compiler hands you a 3-byte
            blob. The digit packing lives in TS 24.008 §10.5.1.3.
    • 
          
  • It does not ingest a spec PDF. Paste clean ASN.1. Text extracted
            from a PDF has comments broken mid-sentence and OIDs split mid-identifier.
    • 
          
  • It does not handle Profile Elements — those are not ASN.1. See the
            Byte inspector tab for a demonstration.
    • 
        

        
Which GSMA specs are actually ASN.1

        

          
SGP.02

      How the structure view works, and its limits
      

        
Why this is not read from the compiler

        

          The obvious approach is to render the parsed module out of
          rasn-compiler. That is not possible through its public API:
          Compiler.state is private with no accessor, the lexer
          module holding the parser entry point is private, and compile()
          consumes self and returns only the generated text.
        

        

          So the structure is extracted from the source text directly, by
          web/structure.js. It reads SEQUENCE / SET bodies, CHOICE
          alternatives, ENUMERATED items, type aliases, tags and constraints.
        

        
What it does not read

        
    
          
  • Parameterised types and information object classes — reported as opaque
            rather than guessed at.
    • 
          
  • IMPORTS — names referenced but not defined here are listed as
            unresolved, which is usually a missing import rather than an error.
    • 
          
  • Constraint semantics beyond SIZE and numeric ranges, which are shown
            verbatim.
    •

      Encoding rules: what is implemented, and what is not
      

        
Why encoding is done in JavaScript

        

          rasn's codecs are all generic over T: Encode, a Rust
          type that must exist at compile time, and rasn::types::Any is an
          opaque byte wrapper with no structure. A browser therefore cannot take an
          arbitrary schema and value and encode them — that would require compiling Rust
          at runtime. Writing TLV is straightforward and works for any schema.
        

        
Implemented

        
    
          
  • DER — canonical, definite length. What the GSMA specs use.
    • 
          
  • BER — same output as DER for these types, since emitting
            deliberately non-canonical BER helps nobody.
    • 
          
  • CER — indefinite length for constructed values, with
            end-of-contents markers.
    • 
          
  • PER — aligned, and partial. Covers BOOLEAN, constrained
            INTEGER, ENUMERATED, OCTET STRING, character strings, SEQUENCE,
            SEQUENCE OF, CHOICE, NULL and OID.
    • 
        

        
Not implemented, and refused rather than guessed

        
    
          
  • Unconstrained PER integers — PER needs a range to know the bit width.
    • 
          
  • PER ranges wider than 65535.
    • 
          
  • Indefinite-length BER on input.
    • 
        

        

          Constraints are enforced, not just displayed. A value violating
          SIZE(10) or (0..255) is rejected, because the
          alternative is bytes that look right and are wrong.

      The TLV-lookalike trap — read this before trusting a decode
      

        
Not every tag-length-value format is ASN.1

        

          A bespoke format can borrow TLV's appearance and break its rules. A conforming
          reader then returns a structurally valid result holding the wrong bytes,
          which is worse than an error.
        

        
Real case — an SGP.22 Profile Element, which is not ASN.1:

        
bytes:            83 0b 80 09 08 29 99 18 11 32 54 76 98

this tool says:   CONTEXT 3 (prim) len=11    <- one opaque blob, no error

actual structure: el(0x83, len=11)
                    └─ el(0x80, len=9)
                         └─ 08 29 99 18 11 32 54 76 98   <- length byte + EF-IMSI

        

          0x83 has the BER constructed bit (0x20) clear, so a conforming
          reader is required to call it primitive and refuse to descend. In
          Profile Elements that byte is an element index whose value does contain
          children. The bit means different things in the two formats, and no flag fixes it.
        

        
The tell

        

          Do not ask "does the first byte look like a tag?". Ask "does the
          specification define this structure in ASN.1 notation?" — look for
          -- ASN1START markers. If the spec describes it in prose, it is not
          ASN.1 whatever its bytes look like.
        

        
Which is which

        

          
ASN.1
SGP.02, SGP.22, SGP.32 — messages, results, certificates

          
Not ASN.1
SGP.22 Profile Elements; ETSI COMPREHENSION-TLV (TS 102.223, TS 31.111)
