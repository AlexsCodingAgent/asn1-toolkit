    About this tool: what it does, and what it deliberately does not
    

      
What it does

      

        Compiles an ASN.1 module to Rust bindings for the
        rasn
        framework, or to TypeScript types. The parser is
        rasn-compiler, compiled to WebAssembly.
      


      
Why it runs in your browser

      

        GSMA specifications are not redistributable, and schemas derived from them
        often inherit that. Nothing is sent anywhere — there is no server to send
        it to. The page is static: no backend, no logging, no rate limit.
      


      
Formatting

      

        Upstream, the Rust backend pipes its output through rustfmt. A
        browser cannot spawn processes, so the raw Rust arrives as a single very
        long line. The TypeScript backend has no formatter at all, so its output
        arrives with odd indentation. This page normalises both locally, with two
        small pretty-printers aimed at the shapes each backend emits.
      

      

        These are not rustfmt or prettier, but the results
        are checked rather than assumed: the Rust output passes
        rustfmt and cargo check against
        rasn 0.28, and the TypeScript output passes
        tsc --noEmit. If you want canonical formatting, save the file
        and run the real tool.
      


      
What it does not do

      
    
        
  • 
          It does not decode mccMnc. SGP.22 declares it
          OCTET STRING (SIZE(3)) "coded as 3GPP TS 24.008". The ASN.1
          says nothing about the internal layout, so a schema compiler gives you a
          3-byte blob and stops. The digit packing is in TS 24.008 §10.5.1.3.
        
    • 
        
  • 
          It does not handle Profile Elements. Those are not ASN.1 at all —
          they are E2 <index> <length> <payload>, a bespoke
          format that looks like TLV and is not. See below.
        
    • 
        
  • 
          It does not ingest a spec PDF. Paste clean ASN.1. Text extracted
          from a PDF has comments broken across lines and OIDs split mid-identifier,
          and no compiler will take it.
        
    • 
      


      
The ASN.1 / TLV-lookalike distinction

      

        Worth knowing before you point this tool at anything: not every
        tag-length-value format is ASN.1. A conforming reader meeting a lookalike
        does not always error — it can return a structurally valid result holding
        the wrong bytes.
      

      
Profile Element, SGP.22 (NOT ASN.1):
    83 0b 80 09 08 29 99 18 11 32 54 76 98

openssl asn1parse says:
    0:d=0  hl=2 l=  11 prim: cont [ 3 ]      <- one opaque blob, no error

the actual structure:
    el(0x83, len=11)
      └─ el(0x80, len=9)
           └─ 08 29 99 18 11 32 54 76 98   <- length byte + EF-IMSI

      

        0x83 has bit 6 clear, so BER is required to call it
        primitive and refuse to descend — but in the Profile Element format that
        byte is an element index that does contain children. Use
        openssl asn1parse on anything you are unsure of; if it returns
        one primitive where you expected a tree, you are looking at a lookalike.
      


      
Which specifications are actually ASN.1

      

        
SGP.22 (RSP)
yes — RSPDefinitions, 98 blocks

        
SGP.32 (IoT)
yes — IPA/eIM definitions

        
ETSI TS 102.223 (SIM Toolkit)
no — COMPREHENSION-TLV

        
3GPP TS 31.111 (USIM Toolkit)
no — COMPREHENSION-TLV

      

      

        The two Toolkit specs contain no ASN.1 at all. If you want a SIM Toolkit
        decoder, this is the wrong tool.
      


      
Verified behaviour

      

        Checked against a valid subset of SGP.22 §5.7.2 and Annex H: the module
        header's AUTOMATIC TAGS is honoured,
        SIZE(3) becomes FixedOctetString<3>,
        OPTIONAL becomes Option<…>, and
        [APPLICATION 26] on Iccid is preserved.
